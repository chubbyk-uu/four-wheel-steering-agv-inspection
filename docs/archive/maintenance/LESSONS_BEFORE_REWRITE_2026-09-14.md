# 坑与教训

本项目过程中踩过的坑，按类别汇总。每条给**现象、根因、教训**和出处，供后续少走一遍。
完整的过程叙述在[状态流水存档](../status/STATUS_LOG_2026-09.md)与`results/`里的数值记录，本页只做索引和提炼。

排在最前的是**测量方法**类，因为它们最贵：错误的测量会让后面所有结论一起报废，而且不会报错。

## 一、测量与实验方法

### 1. 通过了，但什么都没测（空过的断言）

`tools/audit_scan_slip.py`的两半用两个不同输入源：比值判据读`capture_blocks.jsonl`元数据，重复行判据靠
`glob('block_*.pgm')`自己找图，`passed`是两者相与。**原图目录被清理或搬走时后一半恒为空，"没有重复行"
自动成立**；而且退出码恒为0，CI里看不出来。同类还有"旋转取消的停止距离"断言——样本为零时也通过。

**教训**：断言必须先证明"有东西可测"。修法是要求至少定位到一张图、逐块按身份配对，并让退出码反映判定。
出处：状态流水2026-09-12"代码评审修掉两处"。

### 2. 一次只改一个变量

排查内存增长时，对照组同时改了两件事（线阵插件是否加载、OptiX场景是否启用），而GPU雷达两边都开着。
结论"属于线阵插件、排除Gazebo"**因此不成立并被撤回**——外部复核用受控对照证明：保留雷达、移除线阵仍是
+1.02 MiB/s，保留OptiX、关闭雷达渲染则持平。

**教训**：对照实验里每多一个同时变化的变量，结论就少一半价值。
出处：[采集进程内存增长](../../issues/CAPTURE_MEMORY_GROWTH.md)。

### 3. 不显著就是不显著，别当成修好了

服务器/GUI拆分后12次启动零失败、改前12次2次失败，看着像修好了，实际`Fisher p=0.478`。当时如实记了
"保留该改动是因为代价为零，**不是**因为改善已被证明"，并记下混杂因素"失败都紧接在GPU重载任务之后"。
2026-09-14复发一次，正是那个条件。

**教训**：小样本的"零失败"什么都不证明；把不显著和混杂因素写进记录，未来的自己才不会误读。
出处：[控制回路停顿](../../issues/CONTROL_LOOP_STALL.md)。

### 4. 结论要标明适用范围

资源对账原结论"RSS 19.53–19.75 GiB，在预算内"，只对它实测的12.7分钟额定任务成立；34.6分钟的0.5 m/s档
当时达30.07 GiB并耗尽主机内存。不是预算被遵守，是任务够短。

**教训**：凡是随某个量增长的指标，结论必须带上那个量的取值范围。
出处：`results/resource_budget_reconciliation.json`的`amended_2026_09_14`。

### 5. 几条已撤回的归因，留着提醒

- "瓦片缓存颠簸"——ABA实验显示槽位32→128对加载/逐出计数影响为**零**，是流式加载的结构性代价。
- "RTF每次启动掉一级"——干净实例里四次连跑加33 GB读洪水都复现不出来。
- "内存增长属于采集插件、排除gz"——见上文第2条。

**教训**：撤回要和原结论同等醒目地记录，否则错误结论会被后续引用。

### 5b. 首尾都在，不等于中间没缺

覆盖审计只比对执行日志的**第一条和最后一条**时间戳，就认定证据覆盖了整块图像。把日志删到只剩首尾两条、
中间挖掉4秒，仍然判`ESTIMATED_COMPLETE`且不报任何问题——而采集期间的对轮窗口正是从同一份日志推出来的，
洞里发生什么都看不见。

**教训**："边界齐全"和"内容完整"是两回事。判据要能区分**记录慢**与**记录丢**——每条执行记录自报
`control_dt_s`，慢拍仍留证据且间隔等于它自报的时长，间隔明显更大才是丢失。19.3万个相邻记录对实测偏差为0，
其中一次0.352 s的慢拍自报正好0.352 s：**任何固定阈值要么误杀它，要么仍然漏掉更小的洞**。

## 二、工具与脚本

### 6. `exit=$?` 不能和命令替换写在同一行

```sh
echo "[$(date)] ... exit=$?"    # 错：$(date) 先执行，把 $? 冲成 0
```
**两次FAULT在进度日志里都显示成exit=0**，直到发现结果文件缺失才暴露。正确做法是先`status=$?`再拼字符串。
出处：`results/speed_tier_closure_attempt.json`。

### 7. `colcon test-result --all` 汇总的是构建目录里的文件

它读`build/`下的xunit XML，**包括测试源文件和CMake注册都已不存在的陈旧产物**。曾有6项虚增混在总数里，
清理后真实通过数从352降到346。

**教训**：测试总数异常增长时先查`build/`里有没有孤儿xunit，别去数源码。

### 8. `pgrep -f` 会匹配到自己，第一个`gz sim`是2 MiB的ruby外壳

用`pgrep -f "[g]z sim"`的方括号形式避免自匹配；服务端要取**RSS最大**的那个匹配，
因为`gz`是ruby脚本、`$0`被改写，第一个匹配往往是2 MiB的包装进程。曾经因此对着包装进程采了一轮内存。

### 9. 别采样到上一轮正在退出的进程

连续两臂对照时，第二臂的探针挑中了第一臂**尚未死透**的服务端，整个采样窗口作废。
修法是要求候选pid晚于本臂的启动器。

**教训**：跨轮次的进程选择要带"这一轮才产生"的判据，不能只按名字和大小。

### 10. scratchpad 会被WSL重启清空

诊断工具写在`/tmp`的会话目录里，`wsl --shutdown`之后全没了。需要跨重启存活的探针要放进仓库
（例如`tools/probe_guest_cpu.py`就是为此进的仓库）。

---

### 10b. 私有构建树会毒化整个 colcon 工作区

Meson 的 cmake 探测在 `build/meson-private` 下留了**两个同名 `MesonTemp` 目录**，colcon 把它们当成包，
以"重复包名"报错退出，**全量`colcon test`一次都跑不起来**。而带`--packages-select`时不报错——
所以它只在"不选包全量跑"时触发，恰恰是发布前最该跑的那一次。

**教训**：任何在工作区内生成第三方构建树的脚本，**建目录的同一步就要写`COLCON_IGNORE`**，
别等踩到再补。注意`local_data`整个被gitignore，手工补的标记进不了仓库，durable的那一半必须在脚本里。

## 三、构建与环境

### 11. 拷贝安装 vs 符号链接：改了源码测的是旧副本

`agv_localization`曾是拷贝安装，测试导入的是几天前的副本，**改了代码测的还是老的**。
`agv_linescan`同样的问题拖到2026-09-14才消除。

根因不是漏敲`--symlink-install`：**`AMENT_CMAKE_SYMLINK_INSTALL`被CMake缓存锁成OFF，
此后每次增量构建都沿用，命令行再怎么带都不翻回来**。唯一可靠的翻转方式是删掉该包的`build/`重建。

**教训**：一次性配置项行为异常时**查缓存，不要查命令行**。

### 12. OptiX包装器会替换`LD_LIBRARY_PATH`

`tools/with_optix_runtime.sh`整体替换库搜索路径，所以ROS必须在包装器**内部**source，
否则rclpy在`librcl_action.so`上失败：

```sh
bash tools/with_optix_runtime.sh bash -c 'source /opt/ros/jazzy/setup.bash; source install/setup.bash; ...'
```
同理，私有Mesa启动器用**绝对路径预加载**，就是为了在这种重置之后仍然生效。

### 13. `set -u` 会破坏 ROS 的 setup.bash

`AMENT_TRACE_SETUP_FILES: unbound variable`。ROS环境脚本不保证在`set -u`下干净，去掉`-u`。

### 14. 只建D3D12的私有Mesa没有软件回退

私有构建`-Dllvm=disabled`、`LIBGL_DRIVERS_PATH`只指向私有目录，**D3D12初始化失败不会退化成软件渲染，
而是直接失败**。这是有意取舍（失败得早、失败得响，好过静默降级产出看着合格的结果），但必须写明。

## 四、宿主与WSL

### 15. `maxCrashDumpCount=0` 是所有取值里最坏的一个

WSL源码里采集线程和内核参数的开关条件都是`>= 0`，而清理函数开头是`if (Limit <= 0) return;`——
**`0`不是"保留0份"，是"开着采集但跳过清理"，无限累积**。只有**负值**才彻底关闭采集。
转储大小约等于进程RSS，全区任务一次可达16–24 GB。

`ulimit -c 0`也没用：`core_pattern`是管道时内核不按`RLIMIT_CORE`抑制。
出处：[关闭段错误与C盘转储](../../issues/GZ_SHUTDOWN_CRASH_DUMPS.md)。

### 16. 实时率会随WSL实例累积而衰减——而且很可能是Mesa泄漏

同配置六次连跑75分钟内RTF从0.9588掉到0.8669，`wsl --shutdown`后恢复。
修掉Mesa命令签名泄漏之后，同实例六次（开机139 s至6712 s）稳定在0.998–0.999，衰减消失。

**教训**：**不记录"开机多久、该实例跑过几次仿真"的RTF数字之间不可比**。这条已写进第6节验收门槛。
出处：`results/realtime_factor_investigation.json`的`amended_2026_09_14`。

---

### 16b. 合法的策略性丢弃，不能被下游当成数据损坏

采集器按策略丢弃不足1000行的尾图，**而丢弃仍然消耗一个块号**。离线校正要求块号从0连续，
于是一次完全合格的全区采集（0.5 m/s那次，9处跳号，首处66→68）**根本无法离线处理**。

**教训**：上游的"合法缺口"必须在下游有**可核验的依据**，而不是靠下游放宽校验。
这里的依据是采集器自己写进原图目录的`tail_discarded`事件；修法是只允许事件记过的那些id缺失，
并且**核验事件本身**（必须自述`0 < rows < minimum_rows`），其余跳号照旧拒绝——
否则"允许缺口"就变成了"任何丢文件都能蒙混过关"。

## 五、参数与默认值

### 17. 区域起点用了默认值，把任务推出可行驶边界

用了默认`--start-x 6`跑100 m，区域变成6→106 m，跑完的制动又扫到112.07 m，越过108 m的可行驶边界，
规划器在开跑前就拒绝了。**正确的是`--start-x 0 --start-y -5`**。

### 18. 两个限值必须有次序关系，而且要在正确的坐标系里

传感器横向门限0.10低于控制器横向权限0.12，任务可以**被自己的控制器正常工作打断**（实测vy=−0.10002）。
第一次修补加的断言`max_position_feedback_m_s < max_scan_lateral_m_s`**也是错的**——它约束的是
**轨道系**的反馈，而传感器门的是**车体系**的横向速度；含前馈的整条指令被旋转进车体系后，
航向误差ψ会漏进`v·sinψ`，额定速度下ψ=0.04 rad单独就贡献0.111 m/s。

**教训**：限值之间的关系要从**可执行包络**推导，不能拍数；而且必须确认两个量在同一个坐标系里。
最终做法是新增采集期航向门限并把横向门限定为`rated×sin(ψ_max)+反馈权限`再留余量。

### 19. 速度门限表达几何约束，形状本身就不对（未解决）

行间距是空间量，一块4096行永远对应1.5 m行进，所以同样的横向速度在0.5 m/s下造成的块内剪切是额定速度的
**6倍**。真正该约束的是`vy/vx`，即每米行进的横向偏移。此项记录在案，尚未改。
