# Review 第一批修复：采集正确性、队列与故障恢复

> 历史实验记录：本文参数、性能和“当前/默认”描述属于当时版本，不作为新版验收。现行550 kg、20 mm/4K/1.5 m、1 m轨迹间距、11 kHz目标见[当前模型基线](LARGE_AGV_REBUILD.md)。历史命令须按现行配置调整，旧16 mm标定不可用于新版；大体积实验资产可能已清理，复现需重新生成。

2026-09-07。本记录描述第一批修复；后续正式 OptiX 接入见 [集成记录](STAGE2_OPTIX_INTEGRATION.md)。

## 已修改

- CUDA 网格和瓦片后端只返回完整有效批次。任一像素的三个曝光样本中有一次无法覆盖有效地表，则整个批次抛出错误；不把部分曝光除以 3 得到的暗像素发布或归档。GPU 内部同时将无效像素置零，但零值不是对外有效性协议。当前平面模型的地表外区域属于采集失败，不代表将来 OptiX 背景射线的语义。
- `CudaTiles::Sample` 必须传入显式起始采集行号，移除内部 `sampledLines`。GZ 在生成采集事件时分配编号；归档少量位置标签沿用该编号。预热不消耗编号，故障后不重置编号，也不伪装缺口为连续扫描。批次内检查编号连续。
- `linescan.yaml` 的 `sampling` 集中配置 GPU 批次、瓦片缓存槽、等待行数、等待任务数、最大墙钟等待与预取距离；GZ 和独立采样台共用批次/缓存设置。默认 256 行、24 槽、2048 等待行、512 等待任务、150 ms 等待上限、4 m 预取。
- 等待队列按行数与任务数双重限制；在入队/出队时检查最老任务的墙钟等待。内存由这些容量及额外一个在途任务、一个部分 GPU 批次共同约束。不是强实时系统：GPU/磁盘调用本身卡住时，不能保证在 150 ms 内抢占该调用。不能用加大队列弥补长期吞吐不足。
- 容量超限、等待超时、采样错误均停止采集并发布状态，物理控制继续。修复原因后，显式再次调用 `/linescan/set_enabled` 启用会退出旧 worker、重建采样器并预热；恢复写入事件并开启新分段。不会自动假装补齐漏采区域，任务层补扫仍待实现。
- 补光参考照度具名为 `referenceIrradiance`，可用 `radiometry.reference_irradiance_relative` 配置，缺省仍为 41。它是固定标定参考，不随当前 LED 功率变化；增加功率仍使图像变亮乃至饱和。默认数值未变，YAML 仅补说明注释，现有标定配置摘要不变。
- 规范明确功能验证、墙钟吞吐和机械运动时间保真度分开报告；保留 11/22 kHz 墙钟目标。

## 验证

- 包测试：39 项、0 错误、0 失败、0 跳过。新增/扩展覆盖单个曝光样本缺失、缺失后重试、任意预热后的噪声分批一致性、固定参考照度、变行数队列容量、任务数量限制、等待超时与清空后恢复。日志 `/tmp/agv_review_fixes_test.log`，摘要 `/tmp/agv_review_fixes_summary.log`。
- GZ：20 km/h、50 m，实时率 1.000096，42 个图块，最终 HOLD。等待队列峰值 19 行/1 任务，最大等待 0.806 ms；256 行采样批次最大 1.409 ms；物理步墙钟间隔最大 1.376 ms。无必需瓦片缺失，连续编号、相邻块间距、末行标签与网格几何检查通过。与过去的性能差异不能全部归因于本次修改，系统负载和缓存状态也会影响结果。
- 故障恢复：在独立测试目录故意缺少 `tile_2_4.pgm`，启用失败，物理时钟继续、停车到 HOLD；未修复时重试仍失败。补回该文件后无需重启 GZ，再次启用并收到一个图块，最终 HOLD。原始跑道数据未修改。日志 `/tmp/agv_review_gz_recovery.log`。这是数据故障的整车恢复测试；容量/超时故障通过队列单元测试，尚未对整车强制注入 GPU 长时间停顿。

等待队列容量为明确的暂定预算，不是“P99×3 就能保证不溢出”的承诺。元数据报告实际行数峰值与最大等待；验收脚本按实际 `cuda_batch_rows` 计算批次延迟预算，并检查队列门限。
