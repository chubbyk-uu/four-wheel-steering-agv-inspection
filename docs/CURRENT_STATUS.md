2026-09-14发现并记录一个**会阻断长任务验收的宿主问题**：`gz sim`服务端每次关闭都段错误（退出时卸载库与存活线程竞争，与本项目插件无关，去掉线阵插件同样复现），而WSL的`core_pattern`把约等于RSS的整份core写进Windows C盘。静止场景实测单份2.9–3.0 GB，按全区任务20–30 GiB峰值外推单次约16–24 GB。**`ulimit -c 0`与`.wslconfig`的`maxCrashDumpCount=0`实测都不能抑制**（重启后连续4次崩溃累积4份）；WSL源码确认`0`是跳过清理的最坏取值，采集与内核参数的开关条件都是`>= 0`，**只有负值才彻底关闭采集**。已改为`maxCrashDumpCount=-1`并**重启后实测生效**：`/proc/cmdline`不再含`WSL_ENABLE_CRASH_DUMP=1`，`core_pattern`由管道变回普通`core`，同一最小程序再崩已不产生任何转储。该风险解除。见[关闭段错误与C盘转储](issues/GZ_SHUTDOWN_CRASH_DUMPS.md)。

2026-09-14 **`agv_linescan`的拷贝安装陷阱已消除，根因是CMake缓存而不是漏敲命令**。该包与`agv_localization`同为`ament_cmake`+`ament_cmake_python`，README也一直写明要带`--symlink-install`，但`build/agv_linescan/CMakeCache.txt`里`AMENT_CMAKE_SYMLINK_INSTALL:BOOL=OFF`——**某一次漏了这个参数，值被缓存锁住，此后每次增量构建都沿用，命令行再怎么带都不会翻回来**。这正是09-12`agv_localization`坑过一次的同一个机制：改了源码不重建，测的是安装目录里的旧副本。教训是这类"一次性配置项"出问题时**要查缓存而不是查命令**，而且删`build/`重建是唯一可靠的翻转方式。删掉`build/`与`install/`下该包目录后按[README](../README.md)的参数重建，并保留缓存里的`AGV_OPTIX_TEST_RUNTIME`；现在12个`.py`指向`src/`、`libagv_gz_linescan.so`与`agv_optix_scan.ptx`指向`build/`，语义正确：改Python立即生效，改C++仍须重建。**验证**：135项包内测试通过；3×2 m真实任务`ESTIMATED_COMPLETE`/ACQUIRED+HOLD、6块20,805行、RTF 0.9993——测试不加载gz插件，能出图才说明插件经符号链接被dlopen、PTX也从符号链接解析成功。顺带确认该次任务关闭后`wsl-crashes`仍为空，`maxCrashDumpCount=-1`在真实任务上同样有效。本条只改构建产物，`src/`无变化。

2026-09-14 **传感器横向门限由0.10抬到0.15，并把"门限必须高于控制器权限"写成断言**（缺陷一）。原因见本页同日条目：`max_position_feedback_m_s`＝0.12钳的是二维反馈向量的模，所以横向指令上界就是0.12，而传感器门限是0.10，任务可以被自己的控制器正常工作打断。**抬高是用户的决定，理由经核算后修正**：这个门限管的**不是拖影**——曝光20 µs，横向0.10 m/s在一次曝光内只把线挪2.0 µm＝0.0055像素，抬到0.15也才0.008像素；它真正限制的是**块内几何剪切**（整块的横向位置在采集过程中漂移），而剪切逐行记录在位姿标签里、后期可完整还原。所以让后期处理去面对它是合理的，损失的是几何规整性而不是信息。取0.15＝控制器权限0.12加25%余量。新增两条断言（`test_operator.py`）：`max_position_feedback_m_s < max_scan_lateral_m_s`、`max_heading_feedback_rad_s < max_yaw_rate_rad_s`，且各留20%余量——**只改数字不加约束，同样的间歇故障会在新门限上重演**。偏航那一对本来就是对的（0.06 < 0.08，实测峰值仅0.011），顺手一并守住。**一条记下但本轮不改的形状问题**：行间距是空间量，一块4096行永远对应1.5 m行进，所以采完一块的**时间**随速度成反比（额定0.54 s、1.0档1.50 s、0.5档3.00 s），同样的横向速度在0.5 m/s下的块内剪切是额定速度的6倍（0.15 m/s时450 mm，约幅宽的30%，而名义道间重叠只有0.5 m）。**用速度门限表达"可接受的几何"，形状本身是错的**，真正该约束的是`vy/vx`即每米行进的横向偏移；这与本次故障无关，另行处理。360项自动测试通过。

2026-09-14 **内存增长再切两刀：不是堆上的小对象，是大块匿名映射；并非只在采集时发生**。第二刀（车全程静止、一行不产）：插件**只要加载着就以2.23 MiB/s增长**，开启采集后2.39 MiB/s，二者几乎一样——所以真实任务的9.7 MiB/s拆成约2.3的"常在增长"加约7.4的"行驶产行才有"。这也**更正了前一条的对照口径**：那次的"无采集"其实是插件根本没加载，分不清这两层。第三刀（每5秒读`/proc/<gz sim>/maps`与`smaps_rollup`，按映射种类分组）：**`heap`(brk)从220到245 MiB基本持平、`anon_small`从97到108 MiB持平、文件映射持平，全部增长都在大块匿名映射的驻留页上**——85秒内新增20个≥8 MiB的匿名映射、每4.3秒一个、**每个对应19.8 MiB的RSS**。一块图像的像素正好是16.0 MiB，量级吻合，但该窗口内任务只归档了6块，**所以不是"每归档一块漏一块"**。据此排除：C++容器里的小对象累积（那会撑大brk堆）、瓦片缓存与位姿历史（都已有界且在别的预算上）。**下一步**：找出采集路径里那个约16–20 MiB、每约4秒发生一次且不被复用的分配；按尺寸最像ROS图像发布路径，按节奏最像逐次曝光的渲染批。工具受限：本机没有heaptrack/valgrind，`/proc`映射分析是在不重编的前提下能做到的最细粒度。**问题已单独整理成可外传的说明**：[采集进程内存持续增长](issues/CAPTURE_MEMORY_GROWTH.md)，含环境版本、系统结构、三次测量、已排除项、矛盾线索与复现方式。见[采集内存增长](../results/capture_memory_growth.json)。

2026-09-14 **内存增长已定位到采集路径，不是gz本身**。按进程每2秒采样跑同一个3×2 m任务，一次开OptiX采集、一次关掉：**开采集时`gz sim`在场景载入完成后的稳态段从3290 MiB@24s涨到3873 MiB@84s，斜率+9.7 MiB/s；关掉采集时同一进程483→511 MiB、斜率+0.5 MiB/s**，相差二十倍。其余进程都不构成量级：RViz全程持平324 MiB，`mission_operator`涨到98 MiB后持平（审计时再+41），ekf +20、测量适配器 +37、桥 +6 MiB。已排除的几处：传感器位姿历史每次push后裁到8条；C++归档写队列硬限2块在飞；瓦片缓存固定32槽且在显存上。**尚不知道采集路径里累积的是什么**——增长速率不随像素产出走（额定任务每秒产生的行数是0.5 m/s的六倍，涨得反而更慢），所以"保留的图像缓冲"单独解释不了。下一步要按分配点而不是按进程去看gz的堆，首先怀疑逐次曝光产生的结构（它们是按行而不是按块生成的）。见[采集内存增长](../results/capture_memory_growth.json)。
