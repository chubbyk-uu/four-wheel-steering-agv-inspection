# 100 m 场景载入时间

更新：2026-09-17。相关：[道路资产](../ROAD_ASSETS.md)、[当前状态](../CURRENT_STATUS.md)。

最新结果：保留全部精细网格、贴图和启动就绪保护，优化独立OptiX OBJ读取后，默认GUI/RViz短任务的底盘就绪55.7→50.3 s、任务可开始64.3→57.9 s。一组同机热缓存前后实测，尚不能承诺固定启动时限。见[复核报告](../../results/startup_review_20260917.json)。下表的63.7/51.8 s是旧的内存平台口径，不是任务就绪时间。

## 实测预算（干净实例，`inspection.launch.py` 默认 100 m 道路，逐进程 RSS 采样）

改动前，从启动到内存平台约 **63.7 s**、峰值 **9.75 GiB**：

| 阶段 | 耗时 | 内容 |
|---|---|---|
| 启动前 | **16 s** | 仿真进程尚未启动。`shared_scene.validate` 8.6 s + `build_road_display` 5.9 s，单线程串行 |
| gz **server** 加载 | 25 s | ruby 进程 0 → **4.70 GiB** |
| rviz2 | 6 s | 276 MiB（低清代理，已是正确做法） |
| gz **GUI** 加载 | 17 s | 第二个 ruby 进程 0 → **4.25 GiB** |

根因是**同一份路面被重复加载**。`world.sdf` 里 48 个 `terrain_N` 模型的 `<visual>`
指向的就是 OptiX 成像用的那批 OBJ（**7.71 M 三角面**，自适应加密、最细 0.269 mm，另加 96 张
1054×1920 PNG）。gz server（其 `Sensors` 系统要为两个 `gpu_lidar` 建渲染场景）和
gz GUI **各自独立建一遍 Ogre2 场景**，合计 8.95 GiB，占峰值内存 90%。
launch 进程在两者之前又把 2.0 GB OBJ 解析一遍做校验。

## 已做：复用启动前的派生结果（`agv_linescan/derived_cache.py`）

两项都是资产字节的纯函数，而资产在多次运行之间不变：

| | 冷 | 热 | 省 |
|---|---|---|---|
| `shared_scene.validate` | 8.62 s | **2.09 s** | 6.5 s |
| `build_road_display` | 5.61 s | **0.16 s** | 5.5 s |

端到端（同一台机器、干净实例、逐进程采样）：

| | gz server 起 | gz GUI 起 | 到达平台 | 峰值 |
|---|---|---|---|---|
| 改动前 | 18.1 s | 49.3 s | **63.7 s** | 9.75 GiB |
| 改动后（热缓存） | **4.0 s** | **35.4 s** | **51.8 s** | 9.69 GiB |

整条链前移约 14 s，平台提前 **11.9 s**。GUI 不是按墙钟定时，而是挂在 `spawner`
退出后 `gui_start_delay`（默认 6 s，`sim.launch.py:316`），所以前端省下的时间会
如实传导到后面，不会被固定等待吃掉。峰值内存不变——这条改的是时间，不是内存。

> 测量注意：第一次热测量读数为"无改善"，是因为上一轮的 gz 进程尚未退出、两个采样
> 脚本又写同一个文件。每次测量前必须确认无残留 `ruby`/`rviz2` 进程，采样文件按运行
> 区分。全区验收一贯要求的"干净实例"前提，同样适用于计时测量。

`validate` 的 8.6 s 里 `digest` 只占 1.59 s（2.43 GB），`read_obj` 1.27 s，
**`validate_proxy` 占 5.49 s**——它把 7.7 M 三角面读回来、对代理高度场逐顶点和
逐面重采样。缓存的正是这一段推导。

### 缓存键的性质（这是关键，不是实现细节）

- 键**只由已验证的内容构成**：资产条目（内含其网格与各代理文件的 sha256）、
  它所对照的 `ground_material` 与 `display_uv_projection`，以及**检查代码自身的
  源码指纹**。改了检查逻辑，所有条目自动失效，不依赖手工改版本号。
- **绝不使用路径、大小或 mtime。** 会因就地改写而失效的缓存，不值这几秒。
- **命中只跳过推导，不跳过任何完整性检查。** 命中路径照样 digest 全部代理侧文件
  （`proxy_files()` 枚举，1.09 GB、约 0.7 s），就是未命中路径本来会验的那些；
  `build_road_display` 在查缓存**之前**就校验全部源纹理哈希。
- 目录条目的 `.complete` 标记最后写入，崩溃或磁盘满留下的半份拷贝读作未命中。

存储默认在 `$XDG_CACHE_HOME/agv-4wids`（100 m 道路约 68 MB，其中 road_display 代理
68 MB、48 个 scene_geometry 条目各不足 1 KB）。`AGV_DERIVED_CACHE_DIR` 可改位置，
`AGV_DERIVED_CACHE=off` 强制每次重做。测试由两个包各自的 `test/conftest.py` 隔离到
`tmp_path`——否则上一轮留下的条目会让一个已经不再触发的检查看起来仍是绿的。

回归见 `src/agv_linescan/test/test_derived_cache.py`：命中后篡改代理文件与篡改光学
网格都仍被拒；`proxy_files()` 对两种代理方法都覆盖全部带 sha256 的条目；改动检查
代码会改变指纹；半份目录条目与损坏的 JSON 都读作未命中。

### 先纠正本文早先的依据

说"±2 mm 起伏用不着 1.6 cm 网格"是错的，0.4 面/cm² 是无意义的面积平均。
`reference_terrain_4` 实测：**2.5% 的三角面（9,311 个，边长最大 114 mm）覆盖 99.5%
的面积**，其余 97.5%（356,489 个，边长 **0.269 mm**）只覆盖 0.5%。网格**已经自适应
加密**，预算几乎全花在亚毫米级的裂缝与接缝几何上，平坦路面早已很省。所以能做的不是
"降采样"，而是把缺陷几何压平，外观交给 color/normal 贴图（texel 0.25 mm，本来就是它
在表现裂缝）。

### 网格：直接复用碰撞代理的几何

有物理高度场时 terrain 模型**没有 `<collision>` 元素**，那 48 个
`terrain_N_collision.obj` 是被验证却不被 gz 加载的产物。它们正是**源高度场按自身
20 cm 栅格采样、缺陷已压平**的面，且 `validate_layered_proxy` 已对高度场校验过。
生成器只补 UV（用仓库自带的 `validate_display_uv` 校验，48/48 通过），不改那些文件本身。

| | 光学（现状） | 显示（候选） | 比值 |
|---|---|---|---|
| 三角面 | 7,712,280 | **92,508** | **83×** |
| OBJ 磁盘 | 1.03 GB | **8.7 MB** | 118× |
| 几何内存估算 | 740 MB | **8.9 MB** | 83× |

**保真度可以精确陈述**：缺陷之外与被成像的面**逐点相同**；缺陷之内是压平的参考平面，
差值上界就是 `max_surface_deviation_m`（**3 mm**），面积由 `shallow_rectangle` 封顶
1%、实测 **0.11%**。这三个数都由现有验证器强制，不是新引入的假设。

### 贴图：减半，含两项必要修正

| | 现状 1054×1920 | 候选 527×960 | 比值 |
|---|---|---|---|
| PNG 磁盘 | 581.4 MB | **124.8 MB** | 4.7× |
| 解码+mipmap 显存估算 | 1036 MB | **259 MB** | 4.0× |
| 地面分辨率 | 4.0–4.7 mm/px | 8.0–9.5 mm/px | RViz 现用 8.9 |

两项修正经实测都是必要的，不是讲究：**法线图**若直接缩放，归一化前最大偏离单位长度
**0.625**（裂缝棱边处相邻法线方向差异大）；**颜色**在线性光下平均与直接在 sRGB 下平均
最大差 **39.9 个灰阶**。顺带发现 `build_road_display` 现在正是用 PIL `thumbnail` 在
sRGB 下缩的，RViz 代理在棱边和标线处有这个量级的误差——既有问题，非本次引入。

### 有一块对不上，不要按数据量外推

两项合计数据量 1776 → 268 MB（6.6×），但实测每个 gz 进程的 Ogre2 场景是 **4.25 GiB**，
**还有约 2.6 GiB 没有归属**。合理猜测是 Ogre2 的 CPU 影子副本、索引缓冲与顶点格式展开，
**未测**。所以不承诺收益数字，这正是四组矩阵要回答的。

### 分工：网格省时间，贴图省显存

96 张贴图解码实测只要 4.06 s，减半后约 1 s——时间上不显著。而 1.03 GB 的 ASCII OBJ
交给 assimp 解析大概是 server 那段加载的主体：作为量级参照，同一批 OBJ 由独立的 OptiX
读取器读一遍就要 6.38 s（优化后 1.60 s），assimp 还要建场景图与缓冲。
**目标是缩短就绪时间，因此先做网格；贴图那半留给显存。**

### 契约变更（第 1 步，已完成；资产仍未改）

`display_mesh` 是资产条目下的**可选**字段 `{mesh, sha256, triangles}`。**不声明时行为
与改动前完全一致**——三个真实资产
（`*_2mm_20cm_heightmap_v1`、`*_rough_2mm_20cm_v1`、`20m_v1`）重跑 `validate` 均通过，
且都不含该字段。schema 保持 `v1`，C++ 侧不必重建。

声明后 `validate` 不能再断言"两者是同一个文件"，改为**约束两者能差多少**：

| 检查 | 目的 |
|---|---|
| 与 manifest 声明的 sha256 一致、且位于 manifest 同目录 | 与其他所有文件同一规矩 |
| 声明的 `triangles` 必须等于实际面数 | 报告拆分的读取器不可能报假数 |
| `validate_display_uv` 跑在**显示网格**上 | UV 投影一致（原先只跑光学网格） |
| XY 包围盒与光学网格一致（1e-6） | 挡住"盖错地方/被截断" |
| z 范围不超出光学网格 ± `max_surface_deviation_m` | 挡住"根本不是这条路" |
| `world.sdf` 的 `<visual>` 必须指向它 | 声明了却不用 = 拒绝 |

**这些边界不证明两个面逐点相同，也不打算证明**——文档里必须这么说。

缓存侧：`proxy_files` 改名 `checked_geometry_files` 并纳入显示网格，保持"命中路径摘要
的文件与未命中路径完全相同"这条不变量在**一处**表达；回归含"命中后篡改显示网格仍被拒"。

`check_full_road.py` 的 `visual_optix_triangles` 已拆成 `optix_triangles` 与
`gz_display_triangles`（旧字段名留在历史 results 文件里，当时 visual 确实等于 optix，
不回改）。回归见 `test_display_mesh.py`（11 项）与 `test_derived_cache.py`。

## 2026-09-17缓存审查修正

缓存方向保留，但修复了命中目录已存在时的破坏性回退：旧`copytree`报错后会删除调用者原目录。现在先拒绝已有目标，只清理本次创建的目录。目录缓存新增内容摘要，缺文件、内容损坏或元数据损坏均回退重建；几何缓存检查返回值结构及预期碰撞文件名，避免损坏JSON导致启动失败。几何检查指纹同时涵盖实际加载的原生OBJ解析器二进制，重编译解析器不再沿用旧检查结果。布局升级v2，第一次启动会重建派生缓存。

21项缓存/道路显示针对性测试通过，包含原目录不丢失、缓存内容损坏重建及几何缓存错误类型回退。

## 验证设计的前置：任务级像素相等判据不可用（已实测）

轻量显示资产的验证曾计划用"固定轨迹下 OptiX 像素一致"作强判据。**先测了这个判据本身
是否可用：同参数、同出厂种子(20260908)、各自干净实例，连跑两次 3×2 m 短程采集。**
两次都通过（ACQUIRED/HOLD、ESTIMATED_COMPLETE、各 6 块）。结果：

| | 值 |
|---|---|
| 6 块 PGM 逐字节相同 | **0 块** |
| 同一 `global_line` 的 Δx | **−239.16 mm，全块恒定**（= **654.0 个行距**）|
| Δy | 10–14 mm（≈ **39 像素**横向）|
| 首行仿真时刻差 | **11.165 s** |
| 总行数 | 22,235 vs 22,160 |

**差异与渲染无关。** Δx 在整块内恒定（239.16→239.83 mm）而非累积漂移，说明是**起扫
位置差**，不是轨迹发散；两张图拍的是错开 654 行、横向错开 39 像素的两段路。种子固定
只保证每条噪声流的抽取顺序确定，**抽取次数取决于按墙钟推进的调度**，采集使能握手因此
落在接近段的不同位置。渲染本身是否确定**未测**，也不需要测——见下。

**因此验证要这样设计**：

1. **强判据改为静态的**：OptiX 走 `LoadScene`，输入就是 `manifest['assets']`。断言该列表
   及其各 mesh 的 sha256 逐字节未变，即**精确证明成像输入未改变**，不需要跑任务。
2. **`render` 后端靠启动期互斥保证**，不靠像素比对（见上文：同一 server 进程只有一个
   Ogre2 场景，无法让雷达用轻量而 render 用精细）。
3. **任务级 A/B 降为带容差的冒烟测试**：块数、总行数、滑移审计、几何审计按现有验收判据判，
   **不得使用像素相等**。

数据见 `results/capture_run_determinism.json`。这条对拼接阶段同样适用：任何"重跑对比"
都必须是带容差的，本仓库没有逐字节可复现的任务级基线。
