# Gazebo / Ogre2 多行批量成像实验

> 历史实验记录：本文参数、性能和“当前/默认”描述属于当时版本，不作为新版验收。现行550 kg、20 mm/4K/1.5 m、1 m轨迹间距、11 kHz目标见[当前模型基线](LARGE_AGV_REBUILD.md)。历史命令须按现行配置调整，旧16 mm标定不可用于新版；大体积实验资产可能已清理，复现需重新生成。

本实验回答一个范围明确的问题：使用 Gazebo 现有公开相机接口，批量提交多个独立线视图，能否明显缩小与 11～22 kHz 的距离？不迁移 Isaac Sim，不替换项目已运行的采集后端。

## 已有瓶颈

开启可见条光后的项目回归记录见 `results/stage2_gazebo_led.json`：273 行，三次曝光共 819 个视图，渲染 12.363 s、读回 3.581 s、场景同步 0.081 s、横向映射 0.010 s。渲染与读回分别占这些阶段合计约 77.1% / 22.3%。即使把读回完全消除，剩余渲染成本也远高于目标，不能只靠减少 ROS 消息或位姿标签解决。

## 实验方法

`benchmark_ogre_batch` 直接使用与项目相同的 Gazebo Rendering / Ogre2 引擎及相机 API。场景为平面、斜线标记、日光和从项目配置重建的 21 个条光聚光灯；另外测移除条光的更轻场景。使用 WSL Mesa D3D12 / RTX 5080，内部仍为 **5120×1**，输出 **4096 像素**，原有横向畸变多项式、20 mm 焦距、20 μs 曝光均保留。

- 每根扫描线有三个不同的曝光采样位姿；相机沿 X 按 20 km/h 运动，行间距 0.29296875 mm。每行的三个真实渲染视图积分后生成 Mono8 行。
- 批次大小 1、4、16 行分别创建 3、12、48 个独立相机。设置所有位姿后统一 `Scene::PreRender`，提交全部视图，最后统一 `PostRender`；每个视图随后读回。
- 分别比较 GPU 刷新 pass 上限 6 与 96。较大上限不保证更快，渲染 pass 不等同于扫描线，阴影也增加工作量。
- 关闭逐视图读回的诊断工况，在总计时结束前仍强制读回最后一个相机作为 GPU 完成屏障，避免把尚未执行完的提交速度当成渲染吞吐。此工况**没有完整图像输出**，不能作为采集验收。
- 三批预热之后计时，分开记录位姿更新、场景准备、相机渲染、结束提交、读回与 CPU 映射。最后的 PGM 归档不在计时内；没有物理、ROS、完整图块逐文件 fsync，因而只用于定位瓶颈，绝不标记完整验收通过。

## 正确性及动态限制

斜线中心满足世界坐标 `y=x`，每根扫描线前进后，其列坐标应移动约一个像素。Python 工具用独立几何公式预测各行中心，检查误差小于 2 像素及首末行的位移，同时将每种批量结果与逐行基线逐像素比较，允许最多 1 DN 的量化差异。这可以检测错误复用同一位姿或同一张图像，而非用输出行数证明采集正确。

**本轮灯光和场景固定，相机按各自时刻移动。** 这是有利于批处理的静态条件，不代表 AGV 上随车灯具和其他物体的状态已经逐曝光同步。Gazebo 的 `Scene.hh` 明确要求在 `PreRender` / `PostRender` 之间不修改场景；一个共享场景批次不能简单地为每个相机使用不同灯具/遮挡物状态。若静态结果足够快，下一步才值得研究独立场景快照或更底层的时序渲染。

本实验也没有把普通面阵图裁成很多扫描线，没有降低横向分辨率，也没有利用静态纹理替代实际 Ogre2 光照。

## 复现

```bash
source /opt/ros/jazzy/setup.bash
colcon build --packages-select agv_linescan > /tmp/agv_batch_build.log 2>&1
source install/setup.bash
python3 tools/benchmark_ogre_linescan.py --output /tmp/agv_batch_new --rows 192 > /tmp/agv_batch_new.log 2>&1
```

输出目录必须不存在。每个工况在独立进程运行，单次最长 240 秒；完整日志保存，结果见每个子目录的 `summary.json`、`scan.pgm` 及总表 `results.json`。`--quick --rows 32` 只运行最小冒烟实验。实验不启动控制器，不发送运动指令。

## 结果（2026-09-06）

[结构化结果](../results/stage2_ogre_batch.json)，原始工况目录 `/tmp/agv_ogre_batch_v1`。各工况采集 192 行；本轮用于识别数量级瓶颈，不作为持续性能验收。

| 每批行数 | GPU 刷新 pass 上限 | 条光灯源数 | 完整读回 | 行/墙钟秒 |
| --- | --- | --- | --- | --- |
| 1 | 6 | 21 | 是 | 20.05 |
| 4 | 6 | 21 | 是 | **21.70** |
| 16 | 6 | 21 | 是 | 10.79 |
| 16 | 96 | 21 | 是 | 8.08 |
| 1 | 6 | 0，仅日光 | 是 | 30.71 |
| 16 | 96 | 0，仅日光 | 是 | **40.98** |
| 16 | 96 | 21 | 否，仅结束屏障 | 14.05 |

六个完整读回工况的斜线位置误差均小于 0.63 像素，批量结果与相同照明条件下的逐行结果**逐像素完全一致，最大差异 0 DN**。因此，负面性能结果不是通过重复帧或错误相机位姿得到的。

带条光最好的批处理仅比逐行提高约 8%，距离 11 kHz 仍约 507 倍。去掉条光的轻场景也仍差约 268 倍。扩大相机池和刷新上限可能反而降低性能；各视图的渲染和阴影工作仍然存在，并不是合并成一次共享的条带光学计算。

阶段计时也不能直接当 GPU 内核耗时：较大的提交上限会把等待推迟到 `Copy`，看上去变成读回耗时，实际包含先前提交的 GPU 工作。结束屏障对照仍然很慢，不能靠省略完整读回宣称高速采集成立。

**结论：不将这次公开 API 多视图批处理接入正式采集链路。** 在当前 WSL D3D12 环境中，它无法解决 11～22 kHz 目标；继续添加随车灯具/动态遮挡逐曝光快照只会增加复杂度。这不证明任何自定义 Ogre2 着色器或原生平台永远无法提高性能，但那些已属于新的渲染器开发，不是本次验证的简单批处理优化。也不能从此结果推断 Isaac Sim 就一定能达到目标。

默认仿真、控制器、CUDA 后端及其既有参数没有因实验而改变。渲染实验进程全部结束。
